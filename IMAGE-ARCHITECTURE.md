# How the official images for Go, Rust and Zig are built, and what V should take from them

A comparison of [`docker-library/golang`](https://github.com/docker-library/golang),
[`rust-lang/docker-rust`](https://github.com/rust-lang/docker-rust) and
[`ziglang/docker-zig`](https://github.com/ziglang/docker-zig) against this
repository, with concrete proposals for this one.

## The short version

Go and Rust do not maintain Dockerfiles. They maintain **templates** and a
manifest, and generate the Dockerfiles from them. This repository maintains 17
hand-written Dockerfiles, and the duplication between them has already cost three
bugs: the missing Boehm GC on Alpine, `:debian` building `FROM
thevlang/vlang:alpine-build`, and a matrix nested under `strategy:` instead of
`strategy.matrix:` — the last of which GitHub refused to register at all, so two
workflows silently published nothing.

That third bug is the tell. A template cannot have the nesting wrong in one place
and right in another, because there is only one place.

## What each project actually does

|  | Go | Rust | Zig | V (here) |
|---|---|---|---|---|
| Dockerfile source | `Dockerfile-linux.template` | 3 templates | one `Dockerfile` | 17 hand-written files |
| Manifest | `versions.json` | `versions.toml` | none | none |
| Generated by | `apply-templates.sh` | `x.py` | n/a | — |
| Channels | releases + `tip` | `stable` + `nightly` | one | `latest` only |
| Bases | bookworm, trixie, alpine 3.23/3.24, windows | bookworm, trixie, alpine 3.21-3.24 | one alpine | alpine, debian, nix, scratch |
| Extra variants | Windows | `slim` | — | `-dev`, `-build`, `-base` |
| Toolchain verification | sha256 **and GPG** | sha256 per arch | none | none |
| Arch handling | runtime `case` in one file | runtime `case` in one file | `uname -m` in the URL | none, relies on buildx |
| Arches published | 9 on debian, 8 on alpine | 5 | 1 | 2 |
| Reproducible timestamps | `SOURCE_DATE_EPOCH`, verified inline | — | — | — |

### Go is the one to study

`Dockerfile-linux.template` is the whole product. It reads a `variant` from the
environment and a `version`, `commit`, `arches` and `sha256` from
`versions.json`, and emits a Dockerfile that:

- picks its own base image from the variant (`alpine:{{ version }}` or
  `buildpack-deps:{{ variant }}-scm`) — so adding a Debian suite is one line,
  not a new file;
- detects the architecture at **build** time with
  `arch="$(dpkg --print-architecture)"` and a `case` statement mapping it to the
  upstream's own arch name, so **one Dockerfile serves nine architectures**;
- verifies the tarball's sha256 **and** its GPG signature against two pinned
  keys, fetching them from a keyserver;
- records `SOURCE_DATE_Epoch` from the tarball, uses it to clamp mtimes, and then
  **asserts** in the build that it worked (`[ "$SOURCE_DATE_EPOCH" = "$epoch" ]`);
- splits into a `build` stage that installs fetch dependencies as a virtual
  package and deletes them again, and a runtime stage that copies only
  `/target/` with `COPY --link`;
- sets `GOTOOLCHAIN=local` with a comment pointing at the issue that made them do
  it.

### Rust is Go with fewer moving parts

Three templates — debian, alpine, slim — plus `versions.toml`, rendered by
`x.py` into `stable/` and `nightly/`. Each rendered file carries the per-arch
sha256 in its `case` block and a `LABEL org.opencontainers.image.source`. The
`slim` variant is what makes the size range work: same compiler, far fewer
packages.

### Zig is a deliberate counter-example

`ziglang/docker-zig` is one 20-line Dockerfile with `ARG ZIGVER`, and its README
says plainly that it exists only for their Drone CI and that "Zig makes Docker
irrelevant. You probably do not need a Docker image to build your Zig
application". It has no verification and no arch handling — `$(uname -m)` is baked
into the download URL, so the image is single-arch by construction.

That is a legitimate position, but it is not the position this repository is in:
V's images are user-facing, published, and consumed by V's own CI.

## Where this repository stands

What is already right, and worth keeping: the two-stage `-base` → `-build` →
runtime split is the same shape Go uses, and the multi-stage "build V, then copy
only what the runtime needs" pattern is right. `Dockerfile.static` is the
equivalent of Rust's `slim` and works well.

What is wrong:

1. **Nothing is verified.** V is cloned from GitHub and built, so there is no
   tarball to checksum — but that is an argument for pinning a commit, which
   `V_REV` now does, and not for having no integrity story at all. Go refuses to
   link a toolchain it cannot verify.
2. **One Dockerfile cannot serve several architectures.** Go's and Rust's do;
   ours rely on `buildx --platform`, which means the arch decision is the
   workflow's, not the image's, and a local `docker build` on arm64 is a separate
   code path nobody tests.
3. **No manifest.** `versions.json` is why Go can publish nine arches across six
   bases and a `tip` channel from 250 lines of template. We have no equivalent,
   so every variant is a hand-maintained file.
4. **Only two architectures.** Go publishes `arm32v5/v6/v7`, `i386`,
   `mips64le`, `ppc64le`, `riscv64` and `s390x` as well. V itself builds for a
   large matrix in its own CI, so the compilers exist.
5. **No `slim` variant.** Rust's `slim` is the size story. Ours is "the compiler
   plus vlib plus a C compiler", which is inherent to V, but nothing marks the
   smallest useful one.

## Proposals, in the order I would do them

1. **Collapse the variants into one template plus a manifest.** One
   `Dockerfile.template` with `{{BASE}}`, `{{PKGS}}` and `{{USER}}` substitutions
   rendered by a small script against a `versions.json` that lists every variant,
   its base, its packages and its arches. This is the change that makes every
   other one cheap, and it is what would have prevented the two bugs above: the
   matrix nesting would exist once, and `debian` could not have been built from
   `alpine-build` because both would come from the same `FROM {{BASE}}`.
2. **Move architecture detection into the Dockerfile.** A `case
   "$(dpkg --print-architecture)"` block that maps to the arch name the V release
   tarballs use, so `Dockerfile` works for every arch without buildx. This is also
   what makes the multi-arch claim in the README true rather than aspirational.
3. **Verify what is downloaded.** Where a tarball is fetched, checksum it and
   fail on mismatch, like Rust's per-arch `sha256`. Where V is cloned, pin the
   commit — which `V_REV` now does — and record it in an OCI label, so
   `org.opencontainers.image.revision` says which V is inside instead of being
   empty.
4. **Add the arches V's own CI already builds for.** Start with `riscv64` and
   `ppc64le` for debian and alpine; both are in V's CI matrix already.
5. **Add a `slim` variant.** Not a smaller V — the compiler and vlib are fixed —
   but the smallest *runtime* for a compiled program, which is the thing most
   users actually want in production and the thing Go and Rust both optimise for.
6. **Make the timestamps reproducible.** `SOURCE_DATE_EPOCH` on the V checkout,
   clamped before the build, asserted afterwards, the way Go does. It costs
   nothing and turns "reproducible" from an adjective into a test.
